---
description: Generate an HTML visualization for S2S FC eval metrics. Usage: /make-scorecard metrics_dirs=PATH[,PATH...] [name=FILENAME]
---

Generate a single HTML report for S2S FC evaluation metrics by calling the repository script:

```bash
python3 scripts/visualize_metrics.py --metrics_dirs <PATH...> --name <NAME>
```

Do not generate `scripts/compare_ckpts.py`. The current visualization path is `scripts/visualize_metrics.py`.

## Arguments

Parse `$ARGUMENTS` as whitespace-delimited `key=value` tokens.

| Key | Meaning |
|---|---|
| `metrics_dirs` | Required unless `output_dir` is provided. One or more paths, comma-separated or whitespace-separated. Each path can be a metrics root, a direct benchmark output dir, or an existing sidecar JSON generated by `visualize_metrics.py`. |
| `output_dir` | Optional compatibility alias for a single metrics root. Use this when the user still provides the old run-all-benchmarks output root. |
| `name` | Output HTML name or path. Default: `scorecard`. If no directory is given, the HTML is written under `asset/`. |

Examples:

```bash
/make-scorecard metrics_dirs=/path/to/ckpt_a,/path/to/ckpt_b name=comparison
/make-scorecard output_dir=/path/to/run_all_output name=scorecard
/make-scorecard metrics_dirs=asset/greedy.json,asset/sampling.json name=comparison
```

## Source Layouts

`scripts/visualize_metrics.py` accepts these source layouts:

- A run root containing benchmark subdirectories such as `vb_nonmcq_<commit>`, `vb_mcq_<commit>`, `fdb_v1_<commit>`, `fdb_v1_5_<commit>`, `fdb_v3_<commit>`, `bba_<commit>`, `bfcl_<commit>`, and `conv_behav_<commit>`.
- A direct benchmark directory containing `eval-results/`.
- A sidecar JSON from an earlier `visualize_metrics.py` run.

When several benchmark folders for the same dataset are found under one metrics root, always select the latest one:

1. Extract short commits from folder names.
2. If every candidate commit exists in this repository's `git log`, use git history order. Newer commits win.
3. If any candidate commit is missing from git history, use local folder modification time for the whole duplicate set. Newer folder mtime wins.

This means a root may contain mixed selected commits, one per dataset.

## Visualization Rules

The HTML contains:

- A summary table across all detected datasets. Datasets with exactly one display metric get one row; datasets with multiple display metrics get one row per metric, so unrelated metrics are not averaged together.
- A `Metric files` column in the summary table. Each entry is shown as `cluster_name:/path/to/metrics.json`; long paths are visually truncated, but hovering over the path expands it and the full text remains copyable.
- Static per-split metric bar charts for datasets present in two or more input sources. The x-axis is the input source name and the y-axis is the metric value.
- Detailed metric tables for every detected dataset.
- Non-comparison metric sections for datasets detected in only one input source.
- Audio examples where the source outputs contain enough audio metadata. Audio examples are grouped under collapsible dataset sections.

For each dataset:

- If the dataset appears in multiple input sources, visualize it in comparison mode.
- If the dataset appears in exactly one input source, visualize it in single-run mode.
- If one input has datasets `A,B,C` and another has `B,D,E`, compare `B`; show `A,C,D,E` as single-run sections.

## Sidecar JSON

For each non-JSON entry in `--metrics_dirs`, `visualize_metrics.py` writes one sidecar JSON containing that source's metrics, selected benchmark directories, headline scores, detailed metrics, and collected audio examples.

Existing HTML and sidecar JSON files with the same resolved output path must be overwritten. Do not preserve old files by adding a timestamp or alternate suffix.

For multiple input dirs, sidecars are named from the final HTML stem plus the input source name, for example:

```text
asset/comparison_ckpt_a.json
asset/comparison_ckpt_b.json
```

These files are per-checkpoint logs. Do not create a separate aggregate JSON for the final HTML.

## Audio Examples

When audio examples are available, categories are listed first, followed by examples for each category. The category shortcut list at the top links into each audio section, and every section includes a link back to the top of Audio Examples.

Example categories are selected in this order:

1. If `OPENAI_API_KEY` and the `openai` Python package are available, use the LLM category label unless `VISUALIZE_METRICS_LLM_CATEGORIES=0` is set.
2. If LLM categorization is unavailable, use dataset-provided category fields or dataset-specific fallbacks, such as VoiceBench split labels, BBA task names, FDB scenario labels, and conv_behav filename-derived session topics.
3. If no category signal is available, use uncategorized good-vs-bad examples.

Print a warning for each dataset/source when an LLM category is not used, including the fallback source and representative categories. BBA records currently expose `category` as the task name, so the fallback is the task/category label. FDB records expose `dataset` plus the scenario split, so the fallback should combine those when possible, for example `Candor - Turn-taking response` or `ICC - Backchannel timing`.

For every rendered audio player, include the local cluster audio path next to the player. Use the same `cluster_name:/path/to/audio.wav` format and the same hover-to-expand behavior as metric file paths.

For comparison mode with `N` sources, each category should prefer contrastive examples:

- Example 1: only source 1 is good, all other sources are bad.
- Example 2: only source 2 is good, all other sources are bad.
- Continue the same rule for all `N` sources.

If no strict contrastive example exists for a source/category, report that no good-vs-bad contrastive sample was found.

For single-run mode, group examples by status such as good, bad, ok, or sample.

Currently supported audio extraction:

| Dataset | Audio support |
|---|---|
| VoiceBench non-MCQ and MCQ | Uses `output_asr.jsonl` or `output.jsonl`, plus VoiceBench result JSONL when present. |
| BBA | Uses `output_asr.jsonl` or `output.jsonl` records with audio paths. |
| FDB v1 and v1.5 | Uses `fdb_prepared/<sample>/input.wav` and `output.wav`. |
| FDB v3 | Uses `fdb_v3_layout/*/output_*.wav` when present. |
| conv_behav | Uses session audio under validation log wav directories. |
| BFCL | Metrics only. No audio examples are emitted because the BFCL output layout currently contains text/function-call JSONL and metrics, but no stable audio artifact path or prepared wav layout for the visualizer to play. |

## Run

Resolve `metrics_dirs`:

- If `metrics_dirs` is provided, split comma-separated values and whitespace values into a path list.
- If only `output_dir` is provided, use it as the sole metrics dir.
- If neither is provided, stop and ask for `metrics_dirs` or `output_dir`.

Resolve `name`:

- Use `scorecard` when omitted.
- Pass it directly to `--name`; the script appends `.html` and writes under `asset/` when no directory is included.

Run:

```bash
python3 scripts/visualize_metrics.py --metrics_dirs <resolved paths...> --name <name>
```

Report:

1. The generated HTML path.
2. The generated sidecar JSON path or paths.
3. The view command: `bash scripts/serve_scorecard.sh --name <html stem>`.
4. Any missing datasets or warnings printed by the script.
